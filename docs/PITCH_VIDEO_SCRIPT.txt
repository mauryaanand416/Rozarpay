PART 4 — SIMPLE-WORDS GLOSSARY (use these phrasings on camera)
====================================================================================

PRECISION
  "Of everything we flagged, how much was REALLY bad."
  High precision = we rarely bother innocent customers.

RECALL
  "Of all the fraud out there, how much did we CATCH."
  High recall = thieves rarely slip through.

THE TRADE-OFF
  "Catching more fraud always means flagging more innocent people.
  The art is choosing WHERE on that line to operate — per action tier."

PR-AUC
  "One number for how well the model separates bad from good across ALL
  thresholds. One point zero is perfect ranking. Ours: zero point nine seven six."

SHAP VALUES
  "For every decision it tells you HOW MUCH each factor pushed the score up
  or down. Think itemized bill for a decision."

LIGHTGBM
  "An industry-standard ML model for table-shaped data — fast, accurate,
  explainable. This family powers risk systems at banks and fintechs."

TIME-BASED SPLIT
  "Train on January-to-August, test on September. Never shuffle time-series
  randomly — that leaks future answers into training."

HASH CHAIN
  "Every log entry carries the fingerprint of the previous one. Change
  anything anywhere, and every fingerprint after it breaks."

CIRCUIT BREAKER
  "If a service keeps failing, stop calling it for sixty seconds and use
  backup behavior instead of hanging or erroring."

PSI / DRIFT
  "Compares today's data shape against training-time shape. Big difference =
  world changed = time to retrain."

HARD GATE
  "A rule ABOVE the AI: for big amounts a human must decide. Bounded autonomy
  — the machine recommends, never decides alone."

SAFE MODE
  "If the model cannot load, the system refuses to guess — everything goes
  to humans. Fail-safe, never fail-open."

SSE (SERVER-SENT EVENTS)
  "A one-way live stream from server to browser. Simpler than WebSockets,
  auto-reconnects, perfect for pushing decisions to a dashboard."

PART 5 — EXPECTED PANEL QUESTIONS & STRONG ANSWERS (20)
====================================================================================

Q1  Why synthetic data? Isn't that cheating?
A   Public labeled UPI-fraud datasets don't exist. I generated traffic
    adversarially — stealth fraud, hard negatives — and documented limits
    honestly in EVALUATION.md. The loader accepts any same-schema CSV;
    IEEE-CIS Kaggle drops in unchanged. The contribution is methodology plus
    a working system, and both transfer to real data.

Q2  Why LightGBM and not deep learning?
A   Tabular payments data is gradient-boosting territory: better accuracy
    per compute, trains in minutes, scores in microseconds, exact SHAP.
    Deep nets would add opacity and cost without accuracy gain here.

Q3  Block-tier precision is 100% — real?
A   On MY held-out set yes — but only over 78% of its subset, deliberately.
    Broad coverage lives in the REVIEW tier at lower precision. Both
    confusion matrices are published; nothing hidden.

Q4  How do you avoid false-blocking legit customers?
A   Three layers: near-certain block threshold, the Rs 40,000 human gate,
    and a fast review queue. Blocking is the last resort, not first.

Q5  How does it plug into real Razorpay infrastructure?
A   Stateless behind an API. SQLite->PostgreSQL via env var, simulator can
    consume Razorpay test-mode webhooks, deploy on Container Apps — configs
    included. LLM already uses Azure OpenAI.

Q6  What about 10k transactions per second?
A   Scoring is microseconds; per-customer history moves to Redis in prod.
    Rate limiting protects now; Container Apps scales horizontally. Hot path
    (score) is separated from cold path (LLM explanation) precisely for load.

Q7  Can someone prompt-inject the LLM to approve fraud?
A   The LLM has NO authority — it writes explanations only. Decisions come
    from model+rules+gate. Injecting the narrator cannot change outcomes.
    Safety by architecture, not by prompt wording.

Q8  What if fraudsters learn the rules?
A   Rules are floors, not the ceiling. The ML layer adapts through the
    retraining loop; PSI drift alerts say WHEN attacker behavior shifted;
    every analyst verdict becomes fresh training signal.

Q9  Only 19 tests?
A   Covering the critical paths: feature parity, tamper detection, gated
    escalation, auth, queue lifecycle. Production roadmap adds load tests
    and shadow-mode evaluation.

Q10 Why SSE not WebSockets?
A   One-way push is exactly our case; SSE auto-reconnects over plain HTTP.
    Dashboard commands use normal REST, so bidirectional sockets add
    complexity without benefit today.

Q11 Where does the Rs 150 friction cost come from?
A   A configurable constant representing review/handling cost per false
    positive. It makes thresholds business-aware rather than purely
    statistical, and merchants can tune it to their economics.

Q12 Is the hash chain legally meaningful?
A   It provides tamper-EVIDENCE, not legal non-repudiation like digital
    signatures with key management. For regulatory grade, sign entries with
    KMS/HSM keys — an explicit next step in the docs.

Q13 How do you know online features match training features?
A   A dedicated pytest computes both paths over the same history and asserts
    equality within tolerance. Parity drift breaks CI before it breaks prod.

Q14 What if the analyst is wrong?
A   Labels record who decided and when; disagreements surface later via
    chargeback outcomes. The audit trail makes misbehavior attributable —
    deterrence plus forensics.

Q15 Cold start — brand-new customer, no history?
A   Velocity features default to zero, ratio defaults neutral; static
    features (geo mismatch, CVV/AVS, card age) still carry the signal.
    New-card high-value rule covers exactly this gap deterministically.

Q16 Multi-currency? International merchants?
A   Schema has currency field; cost model assumes INR today. Extension is
    mechanical: FX normalization in the feature layer and per-currency
    friction constants.

Q17 Why Python/FastAPI and not Java/Spring like bank backends?
A   The ML ecosystem — pandas, LightGBM, SHAP — lives in Python. FastAPI
    gives async performance comparable to JVM frameworks for this workload.
    Polyglot boundary: hot scoring could move to a compiled sidecar later.

Q18 Model bias against certain regions/customers?
A   Features are behavioral, not demographic. Geo mismatch is contextual
    (travel cohort exists as hard negatives). Fairness auditing on real
    outcome data is listed in the roadmap — honest answer: needs real data.

Q19 What happens if two analysts resolve the same review?
A   Optimistic concurrency: first resolve wins; second gets HTTP 409.
    Both attempts would be audited anyway.

Q20 Biggest weakness of the project?
A   Honest answer: synthetic-data dependence until validated on real
    labeled outcomes, and single-node storage. Both have documented,
    concrete migration paths — Postgres via env var, Kaggle dataset via
    drop-in CSV.
